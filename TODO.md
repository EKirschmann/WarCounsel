## Trio capability data from eqltools' picker

**Status:** designed, shelved 2026-07-27. Not started.

`https://eqltools.com/picker/data.js` is a ~105 KB build artifact whose
`capabilities` block covers 40 capabilities × 16 classes, each with the
level the class gains it and often the best magnitude and spell. Computed
for PAL/ENC/MNK it yields:

```
HAS   cc L2 (mez/charm/fear/stun) · slow L9 · haste L15 · fd L17 (MNK)
      heals L1 (PAL) · pets L1 · root L6 · gate L4 · invis L4 · rune L40
LACKS snare · sow · track · ports · lifetap · backstab · iva · petHaste
```

**Why it is worth doing.** Our advisor reasons spell by spell and has no
concept of *capability*. It cannot currently know this trio has no snare
and no SoW — which rules out kiting and makes travel slow, facts that
should shape hunting picks and loadout advice — nor that slow arrives at
L9, an early power spike worth planning around. One compact prompt line
replaces inference the model does badly, and gives the deterministic path
real gates.

**Licensing is settled.** Their `robots.txt` blocks SEO miners and bulk
training harvesters but states: "Building on this data? Cite
eqltools.com". `/sources` adds "A link back is appreciated, not required",
with wiki-derived parts under CC BY-SA 4.0. Building on it with citation
is explicitly invited, and we already link to their atlas.

**Shape it should take** — same as the ZEM table, and for the same
reasons:

- VENDOR a trimmed snapshot (`capabilities.*.byClass` only; their races,
  deities and stat tables are not needed). Do NOT fetch live: the file's
  own header says "generated by pipeline … do not hand-edit", so the
  format can change without notice, it is their bandwidth on every
  consult, and the packaged .exe must work offline.
- `scripts/refresh_picker.py`, mirroring `refresh_zem.py`, refusing a
  fetch that parses to zero capabilities. Record `meta.generatedFrom` and
  `meta.spellPatch` so the snapshot's provenance is visible.
- `trio_capabilities(classes) -> {has, lacks}` helper.
- Attribution in the file header, README, and the advisor output.

**Trap found while prototyping:** six entries return level `None` —
`tierCC`, `tierDps`, `tierHeal`, `manaPool`, `plate`, `weaponCaps`,
`tone`. They are ratings and model values, not level-gated abilities.
Filter them out; emitting "you get plate at level None" is the kind of
nonsense that costs an advisor its credibility.

## Verify Mac and Linux against a real Wine install

**Status:** shipped in v2.1.0, untested on real hardware.

Detection was verified against seven simulated bottle layouts and then end
to end on Ubuntu 25.10 — but with a synthetic game folder, because that box
has no wine or lutris and no EQL install. Nobody has yet pointed it at a
real bottle with the game in it.

Two specific unknowns:

- **`game_running()` is inferred, not observed.** Off Windows it scans the
  process command line for `eqgame`, borrowed from osxEQL's `pgrep -f`
  health check. If it is wrong the `/log on` banner mis-fires. Cosmetic,
  but unverified.
- The probe list may miss a layout. One `find ~ -maxdepth 8 -type d -name
  "EverQuest Legends"` from a real install settles it, and a miss is a
  one-line fix.

## Overlay on WebView2 instead of tkinter

**Status:** deferred by the user, 2026-07.

Every Win32 mechanism the current overlay leans on has no macOS
counterpart (click-through, Scroll Lock as the interact toggle, global
hotkey polling, tray), and macOS will not reliably draw over a fullscreen
Wine game regardless. A WebView2 overlay would also let it share the web
UI's components instead of duplicating them in tkinter drawing calls.

Worth revisiting only if the overlay becomes a priority on Mac; the
section/field switchboard already made the tkinter one considerably more
useful.
